# Targeting Spanish Municipalities in Google Ads

How many of Spain's 8,240 municipalities can actually be targeted, how to set
the campaign up mechanically, and what the coverage limit costs in power.

## Short answer

1. Google Ads names **970** Spanish municipalities that map cleanly to a GADM
   municipality. Not 8,240. They cover **78% of historical Mosquito Alert
   reports**, because the named ones are the larger places.
2. Do **not** paste names into the bulk location box. Use **Criteria IDs**
   (location IDs) via Google Ads Editor or the API. Google strips accents,
   prefixes many entries "Municipality of", uses "Seville" for Sevilla and
   Catalan/Valencian forms elsewhere, and lists 141 Spanish names twice (once as
   City, once as Municipality). Name matching will silently mis-target.
3. To go beyond 970, use **proximity (radius) targeting** with municipality
   centroids. This has no coverage limit but uses circular footprints.
4. Power cost of the limit: MDE **+40%** with named locations only, against
   **+23%** if all 8,240 municipalities are targeted by radius.

Everything below is generated by
`analysis/r/power_analysis/build_google_ads_crosswalk.R` and
`build_targeting_plan.R`, from the geo target table Google publishes at
https://developers.google.com/google-ads/api/data/geotargets (file used:
`geotargets-2026-07-16.csv`, saved to `data/raw/`).

## What Google actually has for Spain

Active geo targets, Country Code `ES`:

| Target Type | Count |
|---|---|
| Postal Code | 1,221 |
| Municipality | 798 |
| City | 591 |
| Neighborhood | 93 |
| Province | 50 |
| District | 40 |
| Autonomous Community | 19 |
| County | 19 |

So 1,389 City + Municipality entries. Note:

- The 50 **Province** entries match Spain's 50 provinces exactly, which is why
  the province design was operationally trivial.
- "Municipality" is a mixed bag: it includes genuine municipalities but also
  comarcas (`Valles Oriental`) and cuadrillas (`Montana Alavesa`).
- 141 names appear as **both** a City and a Municipality — for example
  `Barcelona` is City `1005424` (urban area) and Municipality `9214622`
  (administrative boundary). For a study randomizing municipalities the
  Municipality entry is the right one; the crosswalk prefers it.

After matching to GADM level-4 municipalities:

| Match quality | Municipalities |
|---|---|
| Matched on name + autonomous community | 952 |
| Matched on a nationally unique name | 18 |
| Ambiguous (name not unique, no community match) | 5 |
| No Google entry | 7,265 |

**970 targetable, covering 78.4% of reports.**

## Why some appear in the UI search and others do not

Four separate reasons, all of which the crosswalk handles:

1. **Coverage.** Only ~1,389 of 8,240 Spanish municipalities exist as geo
   targets at all. The rest simply cannot be targeted by name.
2. **Accents are stripped.** Google stores `Malaga`, `Almeria`,
   `Montana Alavesa`. Typing `Málaga` may or may not resolve.
3. **Prefixes.** Many entries are `Municipality of X` (`Municipality of Madrid`,
   `Municipality of Valencia`, `Municipality of Zaragoza`), so searching `Madrid`
   returns something different from what you may intend.
4. **Exonyms and co-official forms.** Sevilla is `Seville`. Elche is `Elx`.
   Sagunto is `Sagunt`. Palma de Mallorca is `Palma`. Castellón de la Plana is
   `Castello de la Plana`. Donostia/San Sebastián is
   `Donostia / San Sebastian`.

The alias list in the crosswalk script covers the highest-volume cases. It is
not exhaustive — sort the unmatched municipalities by report volume and extend
it if any matter to you.

## How to set it up mechanically

### Preferred: Criteria IDs

A Criteria ID is unambiguous; a name is not. `targeting_plan_spain_municipalities.csv`
carries `google_criteria_id` for every targetable municipality.

**Google Ads Editor** (best for a few hundred to a few thousand rows): build a
CSV with one row per campaign/location and paste it in via *Account > Import >
Paste text*. Editor accepts location IDs directly, so no name resolution
happens.

**Google Ads API** is the right tool at this scale, and makes the
randomization reproducible. A campaign location criterion is:

```
CampaignCriterion:
  campaign: "customers/{cid}/campaigns/{campaign_id}"
  location:
    geo_target_constant: "geoTargetConstants/9214622"    # Barcelona municipality
```

Three campaigns, one per arm, each with its ~320 location criteria.

**The UI bulk box** ("Enter another location" > paste, one per line) resolves
strings, not IDs. With 141 duplicated names, stripped accents and
`Municipality of` prefixes, it will silently attach the wrong geography or drop
lines. If you must use it, paste the exact `google_canonical_name` values from
the crosswalk rather than your own spellings, and export the resulting location
list afterwards to verify it against the intended Criteria IDs.

### To exceed 970: proximity targeting

Google Ads accepts a latitude/longitude and a radius, with no dependence on the
geo target database. This is the only route to the ~7,270 unnamed
municipalities. `targeting_plan_spain_municipalities.csv` provides
`centroid_lon`, `centroid_lat` and a `suggested_radius_km` set to the radius of
a circle with the same area as the municipality, floored at the 1 km Google
minimum.

In the API this is `ProximityInfo` with `geo_point`, `radius` and
`radius_units`. Editor supports radius targets in bulk paste.

The cost is boundary fidelity. Spanish municipalities have a median area of
34 km² (10th percentile 9.5 km², 90th 135 km²), and **187 are smaller than a
1 km-radius circle**, so for those the minimum radius necessarily spills over.
Overlapping circles across arms would contaminate the comparison. Two
mitigations: drop municipalities whose circle would overlap a differently-armed
neighbour, or randomize in spatially separated blocks.

## Power consequence

60-day pre/post windows, single wave, three arms, two-margin (hurdle) analysis:

| Scenario | Units | Active | Silent | MDE intensive | MDE extensive | **MDE combined** |
|---|---|---|---|---|---|---|
| All municipalities (needs radius targeting) | 8,240 | 847 | 7,393 | +27% | +60% | **+23%** |
| Google Ads named locations only | 970 | 386 | 584 | +46% | +100% | **+40%** |

Restricting to named locations costs roughly a doubling of the minimum
detectable effect. It is still much better than any province-level design
(+104% to +170%), because even 970 municipalities beat 50 provinces.

Note the named-only subset has a much higher activation rate among its silent
municipalities (14.3% against 2.8% overall) — Google names the larger places, and
larger silent municipalities activate more readily. That helps the extensive
margin per unit but does not compensate for losing 92% of the units.

## Recommendation

Run the campaign in two tiers:

1. **Named geo targets for the 970 matched municipalities.** These carry 78% of
   historical reports and all of the intensive-margin information. Set up by
   Criteria ID through Editor or the API.
2. **Radius targeting for as many of the remaining 7,270 as budget and
   spillover control allow.** These are what make the extensive margin work and
   take the MDE from +40% toward +23%.

Before committing, validate on a small live test that a sample of Criteria IDs
resolves to the intended geography and that low-population municipalities
actually accrue impressions — a geo target that exists in the table but serves
no ads is worse than useless, because it enters the analysis as a treated unit
with no treatment.
